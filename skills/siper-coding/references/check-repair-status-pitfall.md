# 检查修复状态时的完整历史读取陷阱（v0.9.62+）

## 问题场景

用户列出 N 个检查项（如"1. 回复中断修复 2. Markdown渲染 3. toast问题..."），要求逐一核对是否已修复。

**陷阱**：只核对这 N 个检查项就结束，不追溯完整对话历史。

## 为什么这是问题

- 用户的修改请求分散在多个对话轮次中
- 每个轮次被压缩为 compaction summary
- 当前 context 只显示最近的 N 个检查项
- 实际上今天可能提出了 20+ 条修改要求
- 如果不翻历史，会遗漏 10+ 条

## 正确流程

1. **先读完整历史**：`session_search(query="siper", limit=20, sort="oldest")`
2. **提取所有用户请求**：从 compaction summary 的 `User asked:` 字段提取
3. **与已修复列表对比**：列出哪些已修复、哪些未修复、哪些遗漏
4. **再回答用户**：给出完整的检查报告

## 诊断信号

用户说以下任何一句话时，说明你遗漏了：
- "为什么 XX 问题你没有统计"
- "还有多少修改要求你没有统计"
- "你是不是漏了什么"
- "我之前说的 YY 呢"

## 示例：本次会话的教训

用户列出 8 个检查项，我只核对了这 8 个。但今天实际修改要求包括：
- toast 语言问题（i18n key 缺失）
- 语言切换 toast 提示
- 模型配置独立 tab
- 附件图片识别与渲染
- msg-meta 布局调整
- token 统计后端修复
- 列表项连在一起
- 表格后换行
- 段落换行丢失
- 模型配置页面"加载中"
- ...等 20+ 条

遗漏了至少 10 条用户明确提出的要求。
